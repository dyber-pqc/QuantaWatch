# QuantaWatch's own cryptography

A cryptographic posture tool should be transparent about its *own* cryptography.
This page is the authoritative inventory; the machine-readable CycloneDX version
is [`quantawatch.cbom.json`](quantawatch.cbom.json), **generated by QuantaWatch
scanning itself**:

```bash
qw cbom export . --deps-only --recursive -o docs/quantawatch.cbom.json
```

`--deps-only` matters here: the source-code scanner matches crypto patterns in
source, and QuantaWatch's source *is* full of them (detection regexes, algorithm
tables, and test fixtures like AWS's public example key). Running the code
scanner on ourselves would report those as if we used weak crypto — so the
self-CBOM inventories **dependencies**, not source strings.

## Cryptographic dependencies

| Library | Role | Quantum status |
|---------|------|----------------|
| **ml-dsa** (ML-DSA-65, FIPS 204) | Signatures: audit log, evidence packs, CBOM attestation, cert chains | **Post-quantum** |
| **ml-kem** (ML-KEM-768, FIPS 203) | Key encapsulation for session keys | **Post-quantum** |
| **sha3** (SHA3-256, FIPS 202) | Audit hash chain, Merkle tree, all digests | Quantum-resistant (symmetric) |
| **sha2** (SHA-256) | Inbound webhook HMAC, misc digests | Quantum-resistant (symmetric) |
| **hmac** | Webhook signature verification (X-Hub-Signature-256) | Quantum-resistant (symmetric) |
| **argon2** (Argon2id) | Password hashing for admin/API auth | Quantum-resistant (symmetric) |
| **rustls** (+ `ring`) | Classical TLS to LLM providers and scan targets | **Classical** — see below |
| **jsonwebtoken** | OIDC/SSO JWT verification (RS256/ES256) | **Classical asymmetric** |

Symmetric primitives (SHA-2/3, HMAC, Argon2) are quantum-resistant: Grover's
algorithm only halves their effective strength, which the parameter sizes
already account for. They do not require post-quantum migration.

## Known classical-crypto surface (we are transparent about this)

- **Transport to upstreams is classical TLS.** QuantaWatch's outbound
  connections (to LLM providers and to endpoints it scans) use `rustls` with the
  `ring` backend — classical X25519/ECDHE key exchange. QuantaWatch signs its
  *evidence* with post-quantum ML-DSA-65, but its own TLS is not yet hybrid-PQC.
  This is the same finding the tool would raise against any service today.
- **OIDC JWTs are classically signed** (`jsonwebtoken`, RS256/ES256) — inherent
  to the identity providers we integrate with.

## Not captured by the manifest-level CBOM

- **`ring`** (classical crypto, C/assembly) is a *transitive* dependency via
  `rustls`, so it appears as `rustls` above rather than as its own component.
- **SQLite** (bundled via `rusqlite`, C) provides storage, not cryptography, and
  is intentionally not in the crypto inventory.

## Verifying the self-CBOM

Regenerate it and confirm the component set matches (the `serialNumber` and
timestamps are per-run, so the file is a point-in-time snapshot — compare the
component list, not bytes):

```bash
qw cbom export . --deps-only --recursive | jq '.components[].name' | sort
```
